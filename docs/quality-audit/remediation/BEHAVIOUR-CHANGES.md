# Intentional behaviour changes

## RT-05 (K-001, K-005)
- New scheduled function `sweepStuckGrading` (every 15 min): AI-graded submissions still `submitted` more than 20 minutes after `submittedAt` are set to `status: 'pending_review'`, `graded: false`, `gradingError: 'AI grading timed out; teacher review required'`, and their `grading_locks` doc is deleted. Manually graded assignments are skipped (they legitimately stay `submitted`). Needs the new `submissions (status, submittedAt)` composite index in `firestore.indexes.json` deployed before the function runs.
- `onSubmissionCreated`/`onSubmissionUpdated` now run with `timeoutSeconds: 540` and `memory: 1GiB` (previously the 60 s / 256 MiB defaults).
- Grading lease lengthened from 15 min to 10 min (timeout + 60 s); a crashed run can be retried sooner.
- Short-answer questions of one submission are graded up to 3 at a time instead of sequentially. Results and answer order are unchanged; token budget reservations for concurrent calls are made concurrently.
- Grading now operates on the submission re-read inside the lease transaction, not the trigger snapshot.
- Grading errors are logged with `firebase-functions/logger` (structured, with `submissionId`) instead of being swallowed; `console.*` in `functions/src/grading.ts` replaced.
- Sweep scans up to 10 pages of 200 stuck candidates per run (ordered by `submittedAt`), paging past manual-grading submissions so they cannot starve AI ones.
- After one answer fails, no further model calls are started and the trigger waits for in-flight calls before routing to `pending_review` (the lock is never released while calls run).
- `sweepStuckGrading` is exported from `functions/src/index.ts` so it deploys.

## RT-06: admin routes use the admin claim instead of ADMIN_SECRET (C-003)
- `POST /api/admin/firestore`, `POST /api/research/respond`, and the admin actions of `POST /api/auth/teacher-code` (`generate`, `list`, `revoke`) and `POST /api/auth/request-access` (`list`, `approve`, `reject`) now require `Authorization: Bearer <Firebase ID token>` whose token has custom claim `admin: true`.
  - No credentials: 401 (was 401). Signed-in without the claim: 403. The `x-admin-secret` header is ignored; `ADMIN_SECRET` is not read anywhere.
  - Public actions are unchanged: `teacher-code` `validate` and the `request-access` submit form need no credentials.
- Every admin call (allowed or denied) writes an `admin_audit` document: `uid`, `route`, `method`, `action`, `collection`, `outcome`, truncated SHA-256 `ipHash`, `timestamp`. If the audit write fails the request is rejected with 500 (fail closed).
- Admin-claim users do not need a `users/{uid}` profile document.
- `/admin` and `/research/admin` no longer ask for a secret. They show the dashboard to a signed-in user whose token carries the claim; others see a sign-in prompt or "no administrator access".
- Admins are locked out until the owner runs `tools/set-admin-claim.cjs` (see `RT-06-HUMAN.md`).
- `ADMIN_SECRET` removed from `.env.example`.
## RT-04 (F-004, B-003)
- A provider call that fails in transport (timeout, network error) or returns an unreadable body now releases its budget hold and charges the conservative estimate (input bytes / 4 tokens, 0 output) instead of leaving the reservation pending forever. HTTP non-OK responses are unchanged (settled at zero cost).
- A provider response without `usageMetadata` no longer throws; it settles with the same estimate and logs a warning, and the generated text is returned to the caller.
- New scheduled function `expireStaleReservations` (every 15 min): `ai_reservations` still `pending` after 30 minutes are marked `expired` and their `maxCost` is subtracted from `organizations.aiUsageReserved` (floor 0). Expired holds are not charged. Needs the new `ai_reservations (status, createdAt)` composite index deployed; scans up to 10 pages of 200 per run.

## RT-03 (F-002, C-002): landing/research AI spend
- `POST /api/chat/landing` no longer trusts the body `visitorId` (it is ignored). Visitors are identified by a server-issued, HMAC-signed, `httpOnly`, `SameSite=Lax` cookie `scorpio_lv` (1 year, `Secure` in production), set on first response. The 10-message limit is counted per cookie and, additionally, 30 messages per hashed client IP per UTC day (shared school networks still work; clearing cookies no longer resets the limit). The client IP comes from `x-vercel-forwarded-for`, then `x-real-ip` (first entry; `x-forwarded-for` is never read, see `src/lib/client-ip.ts`). When neither header is present no IP is trusted: the per-IP counter and IP-keyed rate limit are skipped and only the cookie and global daily cap apply.
- New 429 `limitReached` responses for visitors who rotate `visitorId` values; counters update in one Firestore transaction (`landing_visitors/c_<id>`, `landing_visitors/ip_<hash>_<day>`).
- New global daily cap (`landing_daily/<yyyy-mm-dd>`, default 2,000 messages, override with `LANDING_DAILY_CAP`). Past it the route returns 503 with `Retry-After`.
- The route now fails closed with a friendly 503 (no provider call) when `LANDING_ORG_ID` is unset, `LANDING_VISITOR_COOKIE_SECRET` is unset, the landing org's budget is exhausted or inactive, or the counter transaction fails (previously Firestore errors were ignored).
- `landing` AI calls are no longer exempt in `src/lib/ai/config.ts`: they require an organization and a successful budget reservation (`AiBudgetError`, a subclass of `Error` with the same message). `research` stays exempt, but the swallowed reservation error is now logged with `console.error`.
- Landing replies are capped at `maxOutputTokens: 512` (previously the 2048 default).
- A warning is logged (`[Landing Chat] ALERT: landing org budget past 80%`) when the landing org has used 80% or more of its budget.
- The existing unit test that asserted a landing call without an organization succeeds was changed to assert it is rejected (that was the fail-open being fixed); the research equivalent is kept.

## RT-07 (F-001, F-006, E-006): AI grading hardening
- Grader rules now travel in the model `systemInstruction` (new support in `callGeminiDirect`; both `src/lib/ai/grading.ts` and `functions/src/grading.ts` use it). The question, rubric and student submission are sent in per-request random tags (`<submission-3f9a1c...>`) and the rules state that tagged content is data, not instructions. The old double-quote interpolation is gone.
- A single validator (`functions/src/grading-schema.ts`, shared by both paths) replaces the two ad-hoc parsers. A score outside 0..10 is no longer clamped: it fails validation and the submission goes to `pending_review` (functions) or the `/api/grade` call returns 502 with the submission set to `pending_review`. Negative, NaN, `null`, array or non-numeric string scores fail the same way. Numeric strings (`"7.5"`) and fractions (`"8/10"`, rescaled to the 0..10 scale) are now accepted (the old string parser was unreachable). Wrong-typed `student_feedback`/`technical_reasoning`/`misconceptions` fail validation; unknown keys are ignored.
- Submissions are routed to `pending_review` instead of auto-finalising when (a) the answer matches an injection heuristic (instructions to ignore rules/rubric, "full marks", "give me 10/100", "score of 10", "you are now", system-prompt wording, look-alike tags), or (b) the model awards the maximum to an answer of at most 12 characters, for a question of at least 40 characters, where the answer is not a number (optionally with a unit) and does not appear in the question's reference/rubric. Pure numbers and answers present in the reference are never flagged. In functions the flagged answer keeps no score (`reviewFlag`, `aiSuggestedScore` are stored for the teacher), no feedback is shown to the student, and the submission gets `graded: false`, `status: 'pending_review'`, `gradingError`. `/api/grade` returns 200 with `{ success: false, pendingReview: true }`.
- `src/lib/ai/assignment.ts` no longer strips `//...` and `/* */` is no longer stripped either on the main parse; JSON containing URLs now survives. AI output that contains JSON comments now falls through to the existing recovery path (and fails with the existing "incomplete or invalid" error if it cannot be recovered).

## RT-14 (D-002, D-003, D-005, D-006): Firestore and Storage rules
- Teachers can now change `visibility` on their own assignments from the client (previously always denied). Only the `visibility` key may change, to `private`, `network` or `global`. A failure now shows a toast on `/teacher/assignments`.
- `notebooks` and `tutor_sessions`: ownership is decided by `studentId` only. A doc whose id equals a user's uid is no longer readable or deletable by that user unless it is a legacy doc with no `studentId` (or does not exist yet, so the first-notebook probe still works). Creating a doc at an id that is an existing user's uid is denied. Creates are limited to the keys the app writes (`studentId,title,content,messages,createdAt,updatedAt`; no `content` for tutor sessions), title at most 200 chars, `content` at most 500000 chars, `messages` a list of at most 2000. Updates may change only `title,content,messages,updatedAt` (tutor: `title,messages,updatedAt`).
- `users/{uid}`: the `email` field can only be written when it equals the `email` claim of the caller's auth token (the app never writes it from the client; email changes go through Firebase Auth).
- Storage: new `resources/{teacherUid}/**` path (teacher-only writes; images, PDF, text/plain, text/csv, mp4, webm, quicktime; under 500 MB; readable by the owner and that teacher's students). The teacher Resources page now uploads there instead of `submissions/{uid}/`, so teacher video uploads work. Existing resource URLs (download tokens under `submissions/`) keep working. Deviation from the ticket: the path is keyed by teacher uid, not `courseId`, because resources may belong to "all classes" (no course).
## RT-23 (H-013): route error and loading boundaries
- A render error on any page now shows a friendly "Something went wrong" card with a "Try again" button instead of the Next.js default screen. For `/student/*` and `/teacher/*` the card renders inside the existing layout (sidebar, chatbot, banner stay); `app/error.tsx` covers other routes and `app/global-error.tsx` (own `<html>/<body>`, inline styles) covers a root layout failure. `reset()` re-renders the segment; navigating elsewhere also clears the error.
- Error details are never shown to users. Each boundary logs only `error.digest` with `console.error("[route-error] <scope>", { digest })`; there is no server-side reporting endpoint yet (see FOLLOWUPS).
- `student/loading.tsx` and `teacher/loading.tsx` show a skeleton (title, three cards, a panel; `role="status"`) inside the layout while a route segment loads, instead of the previous content staying frozen until the new page is ready.

## RT-21 (B-003, E-007): one budget policy (`evaluateBudget`)
- `checkBudget` (the pre-check) now applies the same rules as `reserveBudget`, via `functions/src/budget-policy.ts`. Two cases the pre-check used to let through are now refused up front; `reserveBudget` already refused both, so nobody who could actually spend is affected, only the error appears earlier (and as the pre-check message):
  - a free network with `aiBudgetLimit` above 50 cents is capped at 50 cents (the pre-check used the configured limit);
  - a non-free network with `aiBudgetLimit` 0 or unset is refused (the pre-check treated 0 as unlimited; the reservation already refused it).
- `reserveBudget` decisions and error messages are unchanged. Network creation defaults are unchanged (see HUMAN-TODO).
- Removed the unused `checkAndIncrementUsage` export from `src/lib/usage-limit.ts`.

## RT-09 (C-007): security response headers
- Every response now carries `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=63072000; includeSubDomains` and a `Permissions-Policy`. Defined in `src/lib/security-headers.cjs`, wired in `next.config.mjs`.
- `X-Frame-Options` is SAMEORIGIN, not the ticket's DENY: `/research` embeds its own same-origin PDF in an iframe, which DENY would block. The Desmos calculator iframes are outbound embeds and are unaffected.
- `Permissions-Policy` disables only unused features (camera, geolocation, payment, usb, bluetooth, serial, hid, midi, motion sensors). It keeps `microphone=(self)` (tutor speech input), `fullscreen=(self)` (lockdown mode, demo video) and clipboard read/write for self and `www.desmos.com` (the Desmos iframes ask for it).
- The CSP is `Content-Security-Policy-Report-Only` (owner decision): nothing is blocked. Violations are POSTed to the new `/api/csp-report`, which answers 204 and logs one sanitised `console.warn` line (`[csp-report] violated-directive=... blocked-uri=... document-uri=...`, query strings and fragments removed, 8 KB body cap, 60 lines/minute per server instance). It does not use `checkRateLimit` (that is a Firestore write per report and fails closed without the DB).
- The CSP uses `'unsafe-inline'` for scripts and styles, because the inline scripts in `src/app/layout.tsx` and `src/components/loading-screen.tsx` and Next's bootstrap scripts have no nonce. Dev mode also allows `'unsafe-eval'` and localhost/emulator origins.
## RT-10 (C-008, K-004, B-004): central PII scrubbing and log redaction
- Every text part sent to Gemini through `callGeminiDirect` (contents, string/`prompt` requests, chat history, `systemInstruction`) is now scrubbed once there with the shared `scrubPII` (`functions/src/pii.ts`). Routes that previously sent text unscrubbed (`ai/generate`, `ai/parse`, `ai/synthesize-rubric`, `/api/chat`, landing chat, network limits help) now get a narrower "contact" scrub: only email addresses (and any roster names supplied through `billingContext`) are replaced, with `[EMAIL]` / `[NAME]`. Dates, long decimals, number lists, phone-like and address-like strings in teacher-authored text are NOT touched (tested). The full pattern set still applies to tutor, grading, network portfolio and notebook, which opt in with `scrubLevel: "full"`.
- Scorpio's published support address `rushil@scorpioedu.org` is exempt from email masking (it is in our own tutor and landing prompts); every other address is masked.
- Scrubbing is idempotent: placeholders from an earlier pass are left alone when masking roster names, so a roster name like "Name" no longer turns an existing `[NAME]` into `[[NAME]]`.
- Roster names can now be supplied through `billingContext` (`scrubNames`, helper `withScrubNames`) and are masked in all parts including `systemInstruction`. No route sets them yet: tutor, grading, network portfolio and notebook still mask names themselves on the user-supplied fragments, so the prompts the model sees there are byte-identical to before (pinned by `__tests__/pii-characterization.test.ts`).
- Cloud Function logs print `j***@example.com` instead of the recipient address (`functions/src/index.ts`, `functions/src/lib/email.ts`); lists of recipients print `[redacted]`.
- `functions/src/grading.ts` uses the shared scrubber and also pattern-scrubs the final system/user prompt; the success result is unchanged.

## RT-12: request-body schemas (G-001, G-005, G-009)
New 400s (body errors are `{ error, fields: [{ path, message }] }`; `error` keeps each route's previous text where one existed). Source: `src/lib/api-schema.ts`, `src/lib/schemas/api-bodies.ts`.
- `POST /api/assignments`: fields are an explicit allow-list (title, description, topic, visibility, courseId, dueDate, timeLimit, gradingType, requireWorkSubmission, enableTabDetection, lockdownMode, allowAIHelp, allowCalculator, totalPoints, type, googleFormLink, rubric, questions). Anything else the client sends (teacherId, organizationId, createdAt were overridden anyway) is dropped, not stored. New 400 "Invalid assignment" for: non-string title, unparsable `dueDate`, `visibility` outside private/network/global, `courseId` containing `/`, a question missing `id`/`text`, and over-long strings. Question objects stay loose (extra per-type fields are kept). Invalid question ids/duplicates from `splitAssignmentQuestions` now answer 400 with that message instead of "Unable to authorize request".
- `POST /api/notebook/chat`: `messages` must be a non-empty array (max 500) of `{ role: "user"|"assistant", content: string <= 50000 }`; `notebookContent` a string <= 500000; unknown message keys are stripped. Previously `[]`, non-string content and unknown roles reached the model call or crashed (500). Error text stays "Missing required parameters".
- `POST /api/auth/request-access`: an unknown `action` is now 400 "Invalid action" (it used to fall through to a public submission). Wrong-typed submit fields (for example numeric `name`) are 400 "Missing required fields." instead of a 500. `id` for approve/reject must be a non-empty string without `/` ("Missing request id"). Approve and submit now run in `runTransaction` (G-009), so concurrent approvals/duplicate submits no longer both succeed.
- `POST /api/submissions`: `workFiles` entries are reduced to name/type/size/url/uploadedAt (extra keys are no longer persisted); a null/malformed answer entry is 400 "Invalid answers" (was a TypeError text); a missing or unparsable attachment url is 400 "Invalid attachment". Existing messages ("Invalid submission", "Invalid submission ID", "Too many attachments", "Answer is too long") are unchanged.
- `POST /api/checkout`: non-string or over-long ids, and an `organizationId` with `/`, are 400 "Missing required fields" (the unmapped plan case still answers "Configuration Error").
- `POST /api/grade`: `submissionId` must be a string <= 256 chars without `/`; withAuthorizedRequest already enforced most of this, so no client-visible change.
- RT-12: notebook chat message cap raised 500 -> 2000 by orchestrator to match firestore.rules notebook messages limit (verifier non-blocking note); the 500KB body limit in withAuthorizedRequest still applies.

## RT-13: withAuthorizedRequest error semantics
- Empty or whitespace-only POST body: was 400 "Unable to authorize request"; now reaches the handler, which reads `{}` (the wrapper hands it a request whose body is `{}`). Identity checks still apply, so an empty body on an `identityField` route is 403 "Account mismatch".
- Invalid JSON: was 400 "Unable to authorize request"; now 400 "Invalid JSON". Valid JSON that is not an object (null, number, string, array): was mostly passed through or crashed into 400; now 400 "Invalid request body". 413 "Request too large" is unchanged. No client reads these strings.
- A handler that throws: was 400 "Unable to authorize request"; now 500 `{error:"Internal server error", requestId}` (detail only in server logs). Routes that already catch their own errors (courses, submissions, membership, assignments) are unaffected; routes with no catch (student/enrollment, teacher/network/invites, teacher/students/cleanup, research/respond, auth/teacher-code) now surface a real 500 for unexpected failures. Grading locks are still released.
- Unexpected failure inside the authorisation phase (profile/submission/lock reads, transaction error): was 400; now 500 with a requestId.
- Billing feature: `withAuthorizedRequest` takes an explicit `feature` option instead of matching the URL. Tutor -> "tutor", notebook chat -> "notebook" (as before). `/api/ai/parse`, `/api/ai/generate`, `/api/ai/synthesize-rubric` are now recorded as "ai-parse", "ai-generate", "ai-rubric" (were "navigation"); chat and chat/limits are explicitly "navigation". Without an option the default is grading/portfolio for those resources, else "navigation". The per-user allowance counters only apply to tutor and notebook, so no allowance changes.
- RT-18 `onAssignmentCreated` (K-002): when the assignment has a `courseId`, only students whose `users.courseId` matches are emailed (previously all of the teacher's students in every course). Assignments without a `courseId` still email all of the teacher's students. Each assignment now records `emailsSentAt` in a transaction before sending, so a duplicate delivery of the create event sends nothing; sends run with a concurrency of 5. Trade-off: the claim is made before sending, so a crash mid-batch is not retried (at-most-once).
- RT-18 `onAssignmentDeleted` (K-003): before deleting submissions it now deletes the Storage objects referenced by `workFiles`, only when the download URL resolves to `submissions/{studentId}/...` for that submission's own student (same rule as `/api/teacher/students/cleanup`). A failed object delete is logged and does not stop the Firestore cleanup.
- RT-11 (C-002): routes that had no limiter now answer `429` with a `Retry-After` header once a per-user (per-IP for public routes) budget is spent: tutor 20/min, ai/parse 10/min, ai/synthesize-rubric 30/min, ai/generate-title 30/min, chat/limits 20/min, grade 30/min, network/portfolio 10/min, research 30/min, checkout 10/min, support/report 5/min, auth/session 60/min, auth/register 20/min, public teacher-code and request-access 30 and 20/min per IP, github/stats 30/min per IP, and 120/min per user on the remaining write routes. Numbers and reasoning: `RT-11-LIMITS.md`. Normal classroom use is far below them because they are per uid, not per school IP.
- RT-11: anonymous rate-limit and admin-audit IPs now come from `x-vercel-forwarded-for` / `x-real-ip`, not `x-forwarded-for`. With no such header (Firebase Hosting) teacher-code validate and request-access use a generous global cap of 600/min under `anon_<kind>` (fail open), github/stats is not limited, and admin audit rows record the hash of "unknown-ip"; the per-IP limits only take effect behind Vercel.
- RT-11: the existing chat / generate / notebook limits moved from inside the handlers to the wrapper (same keys and numbers), so they are now charged before body validation: a request that fails validation with 400 now also uses one unit of budget.
- RT-11: rate limit blocks on the old routes now include `Retry-After` (also the landing chat).
